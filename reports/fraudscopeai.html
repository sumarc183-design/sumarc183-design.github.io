Contexte

Pourquoi ce projet

Un modèle de scoring de fraude produit un chiffre. Un enquêteur a besoin d'une explication qu'il peut relire, challenger et documenter.

FraudScope AI reprend une problématique réelle — la détection de fraude sur les remboursements optiques (lunettes, lentilles) en assurance santé — et ajoute une couche GenAI par-dessus un pipeline ML classique. L'objectif n'est jamais de remplacer l'enquêteur ni de conclure à une fraude avérée : le système qualifie un niveau de risque, explique les signaux qui l'ont produit, cite les règles réglementaires applicables, et laisse la décision finale à un humain.

Les données sont entièrement synthétiques, générées par un script dédié pour reproduire une logique métier plausible sans exposer la moindre donnée personnelle ou confidentielle.

Point clé d'architecture : rien n'est câblé en dur. C'est le LLM qui, via function calling, décide s'il doit scorer le dossier, chercher un texte réglementaire, ou rédiger directement le rapport — typiquement score_claim → search_regulation si le score dépasse 40 % → generate_investigation_report.

Un mode offline déterministe court-circuite tout ce schéma : un score heuristique explicable et un retrieval BM25 local produisent un rapport complet sans clé LLM, sans MLflow, sans Qdrant ni Langfuse — utile pour faire tourner la démo instantanément.

Construction

Les 7 phases du projet

Chaque phase a été committée séparément pour garder un historique Git lisible ; toutes les sept sont terminées.

  1. 1

    Dataset synthétique & scoring ML

    data/generate_synthetic_data.py · src/ml/

    20 000 dossiers optiques synthétiques (~12 % de fraude, signal volontairement bruité). Trois modèles comparés — Logistic Regression, Random Forest, XGBoost — sélectionnés par un score robuste pénalisé qui défavorise l'instabilité entre folds plutôt que de ne regarder que l'AUC test.

    Métriques complètes : lift par décile (1 à 10), écart train/test, Brier score, log loss, taux de faux positifs/négatifs.

  2. 2

    RAG réglementaire hybride

    src/rag/ingest.py · src/rag/retriever.py

    Corpus de 6 documents métier (seuils de prix, cohérence DPEC/RC, réclamations groupées, jour de réclamation, plus 2 documents distracteurs hors périmètre — dentaire, hospitalisation) indexé dans Qdrant.

    Retrieval hybride : recherche dense (embeddings multilingues) + BM25 lexical, fusionnés par Reciprocal Rank Fusion — le BM25 rattrape le vocabulaire réglementaire précis que le dense peut manquer.

  3. 3

    Agent LangGraph, function calling réel

    src/agent/graph.py · src/agent/tools.py

    Boucle agent ↔ outils modélisée comme un graphe d'états : le LLM reçoit le dossier, appelle les outils dans l'ordre qu'il juge nécessaire, puis rédige la synthèse finale. Aucun pipeline figé score → rag → rapport — c'est le raisonnement du modèle qui pilote.

  4. 4

    Observabilité Langfuse

    src/eval/langfuse_setup.py

    Chaque exécution est tracée : latence par étape, coût/tokens des appels LLM, lien vers la trace individuelle pour le debug. Le tracing est non bloquant — sans clé Langfuse configurée, l'agent tourne quand même, simplement sans trace.

  5. 5

    Interface Streamlit & export PDF

    streamlit_app/app.py · src/reporting/pdf_export.py

    Formulaire de saisie d'un dossier, rapport affiché en Markdown, puis téléchargeable en PDF (fpdf2) — mise en page minimale mais suffisante pour un livrable archivable par un enquêteur.

  6. 6

    Évaluation RAG en LLM-as-judge maison

    src/eval/rag_eval.py

    RAGAS écarté (conflit de dépendances avec l'écosystème LangGraph 1.x utilisé par l'agent) au profit d'une évaluation maison : trois jugements structurés — faithfulness, answer relevancy, answer correctness — plus Precision@K / Recall@K / NDCG@K calculées sur les sources attendues.

  7. 7

    Mode démo offline

    src/agent/offline.py

    Score heuristique explicable (pondération de signaux métier : prix hors norme, écart DPEC/RC, dimanche, burst prestataire, téléphone invalide) + retrieval BM25 local. Zéro dépendance externe, zéro clé — le projet se démontre en une commande.

Revue de code

Audit & corrections apportées

Deux passes d'audit sur ce dépôt, chaque point vérifié en conditions réelles (tests rejoués, CI GitHub consultée), pas seulement lu sur le diff.

  • Corrigé

    Initialisation Langfuse non paresseuse

    Le client Langfuse s'instanciait au chargement du module, même en mode offline sans clé configurée, déclenchant un warning d'authentification à chaque exécution. Corrigé : construction à la demande dans get_callback_config(), protégée par is_langfuse_configured().

  • Corrigé

    Multi-fournisseur LLM documenté mais absent

    Le README et .env.example annonçaient GPT/OpenAI et Mistral local via Ollama comme alternatives configurables ; aucune des variables associées n'était lue dans le code, câblé uniquement sur Claude. Périmètre assumé et documenté comme Claude-only ; mentions et dépendance openai retirées.

  • Corrigé

    Documentation périmée

    docs/project_card.md listait encore l'ajout de screenshots comme TODO alors qu'ils étaient déjà dans le README. Retiré.

  • Corrigé

    Aucun lockfile de dépendances

    requirements.txt ne fixait que des bornes minimales (>=), risque de dérive silencieuse entre deux installations. requirements.lock.txt ajouté via pip-compile, la CI installe désormais depuis ce fichier.

  • Corrigé

    Images Docker sur :latest

    docker-compose.yml épinglé sur qdrant:v1.18.3 et langfuse:2.95.11 (la ligne Langfuse 3+ exige ClickHouse/Redis/ stockage objet, hors périmètre de ce compose minimal).

  • Corrigé

    Pas de lint ni de scan sécurité en CI

    ruff check . et pip-audit ajoutés au workflow GitHub Actions ; les 18 signalements ruff du premier passage (imports non triés, except trop large, datetime.now() naïf) corrigés avant activation.

  • Auto-détecté & corrigé

    Bug CI : marqueur pywin32 manquant

    Le lockfile généré sous Windows avait perdu le marqueur sys_platform == "win32" sur une dépendance conditionnelle de docker, faisant échouer l'installation sur le runner Linux. Diagnostiqué et corrigé dans la foulée, avec le rationale tracé dans docs/decisions.md.

  • Mineur, non bloquant

    Lockfile sans hashes

    requirements.lock.txt ne vérifie pas l'intégrité binaire des paquets (pip-compile --generate-hashes). pip-audit tourne clean malgré tout ; à envisager seulement si le niveau d'exigence supply-chain doit monter davantage.

Honnêteté du prototype

Limites connues

Documentées par le projet lui-même (docs/limitations.md) — un score élevé n'est jamais une preuve de fraude, la décision reste humaine.

Données & scoring

  • Dataset entièrement synthétique, non transposable tel quel
  • Seuil de risque faible/moyen/élevé encore heuristique
  • Pas d'explicabilité locale (SHAP) pour l'instant
  • Coût métier faux positifs/négatifs non formalisé

RAG & agent

  • Corpus pédagogique de 6 documents, non exhaustif
  • Jeu d'évaluation annoté encore court (11 questions)
  • Pas de human-in-the-loop pour corriger un rapport
  • Dépend du fournisseur/modèle/température du LLM

API & UI

  • Pas d'authentification sur l'API
  • Validation Pydantic de claim_data encore permissive
  • Interface Streamlit : démo, pas un outil métier complet
  • Export PDF simple, sans annexes ni pièces jointes
